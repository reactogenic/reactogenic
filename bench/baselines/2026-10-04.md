### Claim 12: what I could and could not verify

Sources: MDN pages and `mdn/browser-compat-data` (main branch), fetched 2026-10-04.

| Feature | Chrome | Firefox | Safari | MDN status |
| --- | --- | --- | --- | --- |
| `commandfor` / `command` | 135 | 144 | 26.2 | Baseline newly available since December 2025 |
| `anchor-name`, `position-area`, `position-try-fallbacks` | 125–129 | 147 | 26 | Baseline newly available since January 2026 |
| `closedby` on `<dialog>` | 134 | 141 | preview only | Limited availability |

- **WebKit:** I ran `verify.mjs` and a probe (`VER/probe.mjs`) in Playwright's WebKit 26.6. All checks pass and the menu sits in the same place as in Chrome. That build is ahead of stable Safari (it has `closedby`), so it is evidence for the engine, not for a shipped Safari.
- **Stable Safari:** not run. Without `closedby`, clicking the backdrop will not close a dialog there; Escape and the close button still work.
- **Firefox:** not run. Playwright's Firefox 155 would not start in my sandbox ("Could not find profile folder"). By the compat data, Firefox 147 and later has everything the floor uses.
- **Behaviour gaps the checks do not see** (probe output in `VER/probe-chrome.json`, `VER/probe-webkit.json`):
  - no typeahead in menus;
  - Tab moves to the next item and leaves the menu open;
  - no `aria-haspopup` on the trigger;
  - in WebKit, focus does not return to the trigger when the menu closes;
  - the mobile drawer is a non-modal popover (no focus trap, background not inert).
- **Screen readers:** not reviewed by anyone.

### Corrections that change the thresholds

**1. The floor understates JS by about 1.8x once the gaps above are closed.** I added typeahead, Tab-closes, focus return, `aria-haspopup` and a backdrop-click fallback (`VER/parity/parity.mjs`). The result passes `verify.mjs` and the probe in both Chrome and WebKit.

| Page | JS to parse, raw: floor → with parity | JS brotli: floor → with parity |
| --- | ---: | ---: |
| `/` | 921 → 1,669 | 372 → 605 |
| `/getting-started/` | 725 → 1,350 | 291 → 496 |
| `/syntax/` | 1,217 → 1,965 | 477 → 688 |
| `/api/` | 725 → 1,350 | 291 → 496 |
| mean | 897 → 1,584 (1.77x) | 358 → 571 (1.60x) |

T2 allows 2x the floor, so parity alone uses 81–93% of that budget. Either adopt the parity floor as the reference or widen T2. Against React the picture does not change: still about 200x fewer bytes to parse than Astro + Radix.

**2. T4, T5 and T6 depend on packaging and on content size.**

- The author's own inline packaging fails T5 as written (HTML 7,478 B, 1.35x) and passes T4 trivially (0 B external CSS). Astro-vanilla fails T5 (1.14x) for the same reason only. Compare HTML + CSS + JS together.
- Content (`<main>`) is 4,737 B of the 7,527 B mean, 63%. "Page total at most 1.25x" therefore lets the part the compiler controls (2,790 B) grow 1.67x, and the "refuted above 2x" line lets it grow 3.7x. State both thresholds on non-content bytes.
- T9 (script at most 5 ms) has little margin: I measured 4.2 ms on Astro-vanilla `/syntax/` where the author had 3.0.

**3. Per-page files are not the best packaging of the floor.** `d-floor-page` gets almost no cross-page caching (session CSS 6,580 B is the sum of four different files). The inline variant is smaller cold (7,478 vs 7,527 B), equal over the session (29,910 vs 29,816 B) and needs 1 request instead of 3. This supports the author's own point that chunking is a packaging choice, but the recommendation names the wrong variant as the target.

### What the report missed

**1. Most of the floor's JS is application logic, not layout-component behaviour.** Minified sizes of the four snippets in `d-floor/build.mjs`:

| Snippet | Raw | Belongs to |
| --- | ---: | --- |
| `menukeys` | 311 | Dropdown (component) |
| `theme` | 316 | the site: persist and apply the theme |
| `copy` | 196 | the site: copy-to-clipboard buttons |
| `search` | 492 | the site: filter headings, `/` hotkey |

Dialog, drawer and collapsible groups need no JS at all. So 1,004 of 1,315 B (76%) is behaviour that none of SideMenu, Dialog or Dropdown would own. T12 forbids hand-written JS in the site, shell rule S1 forbids event handlers, there are no islands in phase 2, and page-author raw JS is on the deferred list. The reference site therefore cannot be written in phase-2 Reactogenic unless the catalog grows (theme switch, copy button, filter) or those features are dropped from the site. This needs a decision before the target is fixed.

**2. The reference site loops over data.** Side menu links, menu items and search results come from `.map()` over `site.json`. Shell rules S2 and S5 forbid loops, with an open note on compile-time constants (`specs/later/layout.md`, line 131), and "loops over constants in the shell" is on the deferred list. A side menu is not practical without it.

**3. T1–T12 do not separate Reactogenic from Astro.** Astro-vanilla meets every byte, request, CPU and behaviour threshold (after the packaging fix above), its pages contain no script, and it drops a component's CSS and JS from pages that do not use it. The bet as restated ("who writes the platform code") is equally met by any Astro component library. What is specific to Reactogenic is that the same typed-slot TSX component compiles to this output in the shell and renders under React in an island. No threshold tests that.

**4. No compiled-framework baseline.** Every non-floor baseline is React or Astro. Marko, Qwik and Svelte, which also compile components and ship only what is interactive, were not measured, and neither was a small-runtime option such as Preact islands. T3 ("100x below React") is a weak bar without them.

**5. The scale test is the real test of the bet and is listed as optional.** With three components, precision is worth 6.8%. Whether a component-aware compiler "ridiculously" beats a bundle can only show on a catalog of about 20 components, which the author proposes as a follow-up. It should be part of phase 2's exit criteria. I tried Chrome's coverage on Starlight as a quick proxy (`VER/coverage.md`); it reports 4–5% unused CSS, which I do not trust (the stylesheet is in `@layer` blocks), so I draw no conclusion from it.

**6. `measure.mjs` counts every logged request as a full download.** It does not record the method. This only bit the Next prefetch build (claim 8), but fix it before measuring Reactogenic's output with it.

### Does the recommendation hold?

Yes in substance, with amendments. The measurements are sound and reproduce exactly. The direction is right: build on platform primitives, treat chunking as packaging, do not chase bytes below the floor. Before adopting the thresholds:

1. Use the parity floor (mean 1,584 B raw JS) or widen T2.
2. State T4–T6 and the refutation line on non-content bytes, packaging-neutral.
3. Decide where theme, copy and search behaviour come from under T12, and whether the shell may loop over constants.
4. Add a criterion that only Reactogenic can meet (one component source for shell and island) and make the 20-component scale test an exit criterion.
